## 标准、来源与网络

当前只集成 ERC-8004 Identity 和 Reputation。Validation 尚未接入，规范仍是
Draft。接口和 ABI 以官方 contracts 仓库的以下不可变 commit 为准：

<https://github.com/erc-8004/erc-8004-contracts/tree/b9e466c250744a7e06b13dff9d3c2844ed64f825>

Identity/Reputation 的实现版本按 2.0.0 处理。Monad 目标网络固定为 chain
10143；本地测试 fixture 固定为 chain 31337。不能切换到 mainnet，也不能在网络
失败时回退到另一个 chain。两份 RPC 必须在同一个已复验的 canonical/finality
边界上给出一致观察。

官方发布的 testnet 地址可以作为配置预检的起点，但它们本身不是本项目的 live
部署证据，也不能替代实时 code/ABI 检查：

| Registry | Published address | 使用前必须完成 |
| --- | --- | --- |
| Identity | `0x8004A818BFB912233c491871b3d84c89A494BD9e` | 两份 RPC 的实时 code、代理实现和 ABI 检查 |
| Reputation | `0x8004B663056A597Dffe9eCcC1965A193B7388713` | 两份 RPC 的实时 code、代理实现和 ABI 检查 |

项目只接受 operator pin 的 registry、service Agent、owner、receiving wallet
和 URI。不能让访问者从请求参数选择 registry、`agent_id`、payee 或远程 URI，
也不会根据旧地址列表跳过当前 code/hash 检查。

## 受保护配置

Hosted server 通过 `--erc8004-config FILE` 读取配置；公网打包约定的路径是
`/var/lib/agentonomy-web/erc8004.json`。该文件应由当前 `agentonomy-web` 服务
UID 拥有，使用 mode `0600` 的 regular single-link 文件，并由现有的 protected
config reader 加载。其父目录 `/var/lib/agentonomy-web` 应由
`agentonomy-web` 拥有并使用 mode `0700`。它只保存公开的 registry/Agent pin 和
代码 hash，不应包含私钥、助记词、KMS 凭据、AWS session、浏览器 cookie、Agent
token 或交易签名材料。配置不提供 signer、broadcast 或任意 RPC/registry 选择
开关。

签名范围仍独立保存在受保护的 `/etc/agentonomy-commerce/signer.json`；该文件
由 `agentonomy-sign` 拥有并使用 mode `0600`，其父目录使用 mode `0700`。web
服务不得读取或改写 signer 配置，sign 服务账号也不得通过该边界读取 web 的
状态或 registry 配置。

字段必须与下面完全一致。`RegistryConfig.from_dict` 拒绝未知字段和缺失字段；
地址、URI、网络和 hash 仍需经过格式和实时边界校验。

| 字段 | 约束 |
| --- | --- |
| `identity_registry` | operator-pinned ERC-8004 Identity registry 地址 |
| `reputation_registry` | operator-pinned ERC-8004 Reputation registry 地址 |
| `agent_id` | 非负整数；注册尚未完成时为 `null` |
| `agent_owner` | 预期的 service Agent owner 地址，必须和 verified registry state 一致 |
| `agent_uri` | 必须严格等于 `origin + '/agent.json'` |
| `identity_code_hash` | Identity registry proxy/runtime 的 operator-pinned code hash |
| `reputation_code_hash` | Reputation registry proxy/runtime 的 operator-pinned code hash |
| `identity_implementation` | Identity registry implementation 地址；Monad 配置必填 |
| `identity_implementation_code_hash` | Identity implementation runtime code hash；Monad 配置必填 |
| `reputation_implementation` | Reputation registry implementation 地址；Monad 配置必填 |
| `reputation_implementation_code_hash` | Reputation implementation runtime code hash；Monad 配置必填 |

四个 implementation 字段只能在 `local_anvil` 测试 fixture 中同时为 `null`。
Monad 配置必须把 proxy runtime hash、implementation 地址和 implementation
runtime hash 都固定下来。下面是故意不可直接运行的字段形状；尖括号值必须由
operator 通过两份 RPC 的只读检查取得，不能填写示例 hash 来伪造已验证状态：

```json
{
  "identity_registry": "<operator-pinned address>",
  "reputation_registry": "<operator-pinned address>",
  "agent_id": null,
  "agent_owner": "<operator-pinned service-owner address>",
  "agent_uri": "<public-origin>/agent.json",
  "identity_code_hash": "<live identity runtime hash>",
  "reputation_code_hash": "<live reputation runtime hash>",
  "identity_implementation": "<live identity implementation address>",
  "identity_implementation_code_hash": "<live identity implementation runtime hash>",
  "reputation_implementation": "<live reputation implementation address>",
  "reputation_implementation_code_hash": "<live reputation implementation runtime hash>"
}
```

`agent_id: null` 只能表示 registration 尚在准备阶段；在身份真正注册并通过
验证前，不能把服务标记为 active 或允许新购买。`agent_uri` 由服务自身提供
`/agent.json`，adapter 不会任意抓取第三方 URI。

## 只读 CLI 与 registration

CLI 只有以下形状：

```text
python -m scripts.monad.erc8004_registry --config FILE --network-config FILE --origin HTTPS --operation prepare-registration|verify-identity
```

`prepare-registration` 只生成由 pinned service owner 使用的 unsigned
`register(agent_uri)` transaction，并检查 network、registry code 和配置 pin；
它不签名、不发送、不广播，也不接受 credential、signer、KMS、gas payer 或
private-key 选项。`verify-identity` 只读两份 RPC，返回已验证的
`agent_registry`、`agent_id`、`agent_owner`、`agent_wallet`、`agent_uri`、
`chain_id`、`block_number` 和 `block_hash`。实际 registration 和后续的 live
接受必须由受保护的 operator 流程另行完成；当前仍是 pending。

身份检查在每一次新购买前执行，至少核对：

1. chain/network、registry 地址、proxy/runtime code hash 和 implementation
   地址/hash 在同一个已复验边界一致；
   Reputation 的 `getIdentityRegistry()` 还必须返回配置中的 Identity 地址；
2. registry 中的 Agent owner、URI、wallet 与配置 pin 一致；
3. `agent_wallet` 与现有 network payee 完全相同；
4. 两份 RPC 对 identity state、代码和 canonical block 没有分歧。

owner、URI、代码、implementation、network 或 receiving wallet 的任何漂移都会
阻止新购买。这个 guard 不能选择预算、改变 merchant、签名或广播付款。

## registration metadata

只有已注册且已验证的 identity 才能成为 active metadata。`registration-v1`
文档只声明实际存在的 registration 和一个 web endpoint；`x402Support` 固定为
`false`，`supportedTrust` 只包含 `reputation`。文档不会虚构公共 MCP endpoint，
也不会声称支持 x402。Identity + Reputation 是当前集成范围，Validation 以后再
评估。

Hosted 公开读取接口的约定是：

* `GET /agent.json` 返回服务自己的公开 Agent metadata；
* `GET /.well-known/agent-registration.json` 返回上述 registration-v1 metadata；
* `GET /api/agent` 返回当前 verified identity 的状态，未配置或未注册时返回
  unavailable，而不是伪造 Agent；
* `GET /erc8004/feedback/{hash}.json` 只返回已经独立验证并发布的 feedback
  文档。

这些 endpoint 不会把内部 MCP 地址包装成公网能力。真实部署必须使用 HTTPS 和
配置中完全一致的 origin；公网是否可达仍取决于后续 HTTPS rollout 和独立部署
验收。

## 购买、收款与恢复

身份/payee guard 通过后，原有 Core 流程仍必须完整执行：wallet identity、既有
EIP-191 Spending Grant、policy/risk、预算 reservation、execution recheck、
KMS/relayer 固定范围、budget contract 硬上限、双 RPC payment verification 和
audit。ERC-8004 身份证明不能替代其中任何一步。

如果服务 Agent 的 owner、URI 或 receiving wallet 在付款后发生变化，已经付款
的订单仍以原始 immutable purchase、Core receipt、payment proof 和输入 hash
为键恢复；恢复只做原订单交付或查询，不能新建订单来掩盖未知状态。若某个恢复
分支有可能发起付款，它必须重新执行与 execute 完全相同的 identity guard、
policy/risk、reservation 和 execution recheck。付款成功而交付失败时永远只重试
交付，不再次扣款。

## 买方 feedback

Feedback 是买方的可选动作，不是购买授权的一部分。它要求当前登录 cookie、
CSRF 和当前 Core owner proof，并且只能引用该买方持久化的 delivered order、
canonical Core 双 RPC payment proof 和持久化的 SHA-256 `output_hash`。公开文档
不得包含 CSV、report 内容、`input_hash`、grant/signature/session/Agent
credential、内部 tenant ID 或内部 order ID。

Hosted API 的请求形状是：

* `POST /api/purchases/{purchase_id}/feedback/prepare`，body 为
  `{ "score": 0..100 }`；
* `POST /api/purchases/{purchase_id}/feedback/verify`，body 为
  `{ "transaction_hash": "0x..." }`；
* `GET /api/purchases/{purchase_id}/feedback` 查询当前状态，查询不会生成、
  签名或广播交易。

score 必须是严格的整数 0 到 100。prepare 会冻结每个 tenant/order 的
canonical document bytes、feedback URI 和 keccak hash；第二个 score 不能改写
已冻结文档，竞争的 transaction hash 不能覆盖第一次保存的候选 hash。服务端在
RPC 验证前先持久化买方提交的原始 tx hash；pending、unknown 或 RPC 分歧只能
保留原候选，不能自动替换或重发。

浏览器必须按 `prepare -> inspect disclosure -> send` 执行：`prepare` 只生成并
冻结待签交易，页面先展示买方地址、分数、原付款交易和 `output_hash` 摘要；用户
明确点击发送后，连接的钱包才会签名并提交这笔固定的零 value transaction。每个
authenticated wallet/order 的 feedback record 都是单独的持久化记录，与普通
purchase reference 分开，并为每个订单保存独立发送标记，普通状态写入不能清除
该标记。已知候选哈希从两种记录合并，冲突会阻断；查询、刷新和恢复不能生成或
自动发送新的交易。

发送前必须在同源、同一 browser profile 的 tabs 之间取得 `navigator.locks` 独占
锁，并在锁内重新读取 durable record。unknown marker 在钱包调用前写入，因此刷新
或崩溃后仍会阻止重发；不支持 Web Locks 或 localStorage 时，optional feedback
sending 和原候选哈希恢复必须 fail closed。钱包返回 cancellation `4001` 只会在持有 originating
lock 的流程内清除 marker。这个协调边界只覆盖同 origin、同 browser profile，不能
看见其他设备、其他 profile 或 storage 被清除后的 pre-hash unknown attempt；恢复
时要保留原 browser metadata，并先核对原钱包交易。Backend 只在提交 tx hash 后
约束原候选，不能宣称跨设备排除 unknown。

在生成 calldata 前，adapter 会在同一个 verified identity boundary 检查
`isAuthorizedOrOwner(buyer, agent_id)`。这只是 ERC-8004 feedback 的 registry
授权检查，仍必须同时满足当前 Core owner proof、已交付订单和 Core payment
evidence；它不会把买方变成 service Agent owner，也不会扩大买方的消费权限。

买方钱包直接签署固定的零 value Reputation transaction。KMS 不代签 feedback，
也不会因为 feedback 发放 allowance。交易必须是：

```text
from   = connected buyer wallet
to     = pinned reputation_registry
chainId = configured network chain
value  = 0x0
data   = giveFeedback(agentId, score, 0, 'starred', 'csv-reconciliation', origin + '/', feedbackURI, feedbackHash)
```

`verify` 只有在两份 RPC 都证明同一笔 transaction 时才会公开文档：买方/from、
registry/to、chain、完整 calldata、gas/value、成功 receipt、canonical block、
共同 finality、恰好一个匹配的 `NewFeedback` event，以及 verified boundary 的
`readFeedback` state/index 都必须一致。被撤销的历史 feedback 仍保留为可区分的
revoked 状态，不能被伪装成当前有效反馈。

代码和 Identity 绑定在 receipt 区块及最终性边界都要核验。区块 RPC 读取的是
区块结束状态，因此这仍依赖可信的 registry 升级治理：同一区块内升级、执行再
恢复的序列无法只靠这些状态读取识别。本实现没有宣称证明每笔交易执行瞬间的
实现代码；做到这一点需要额外的 execution trace 或证明。

注册 owner 与现有收款地址相同时，参考实现的 `register(string)` 默认
`agentWallet` 就是 owner。若两者不同，须通过 registry 的授权流程另行绑定
收款地址并复验；本 CLI 只准备注册，不会替 operator 修改 Agent wallet。
